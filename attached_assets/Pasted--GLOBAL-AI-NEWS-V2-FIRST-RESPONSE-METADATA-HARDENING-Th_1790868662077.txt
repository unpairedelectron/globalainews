# GLOBAL AI NEWS V2 — FIRST-RESPONSE METADATA HARDENING

The latest hardening pass is complete.

Do NOT publish.

Do NOT modify production editorial data.

Do NOT redesign the UI.

The remaining priority is:

> **Every newly published article must return correct article metadata in the FIRST HTML RESPONSE, without requiring JavaScript execution or a rebuild.**

The current implementation can open a post-build article without rebuilding, but its first HTML response still contains generic metadata until JavaScript runs.

This must be eliminated.

---

# 1. OBJECTIVE

For a newly published article such as:

```text
/article/<slug>
```

the first HTTP response must already contain the correct:

```text
<title>
<meta name="description">
<link rel="canonical">
<meta property="og:title">
<meta property="og:description">
<meta property="og:url">
<meta property="og:image">
<meta name="twitter:card">
<meta name="twitter:title">
<meta name="twitter:description">
<meta name="twitter:image">
```

where applicable.

The response must also contain the correct visible:

```text
H1
author
published date
updated date where applicable
```

without waiting for React hydration.

---

# 2. CURRENT STACK

The current application is:

* Express
* Vite
* React
* Postgres

Do NOT assume this is a Next.js application.

Work within the existing architecture.

Do not introduce Next.js merely to solve metadata.

---

# 3. FIRST: TRACE THE CURRENT REQUEST FLOW

Before changing code, document:

```text
Browser request
    ↓
Express route
    ↓
data lookup
    ↓
HTML/template response
    ↓
Vite/client bundle
    ↓
React hydration
```

Identify exactly where metadata is currently generated.

Determine whether the current behavior is caused by:

* client-side Helmet/head management
* static Vite HTML
* SPA fallback
* Express response handling
* API fetch after page load
* route-level rendering
* metadata being unavailable at request time

Do not guess.

---

# 4. SERVER-GENERATED ARTICLE METADATA

Implement request-time server metadata for article routes.

Conceptually:

```text
GET /article/:slug

        ↓

lookup published article

        ↓

generate HTML shell

        ↓

inject article metadata into <head>

        ↓

return complete initial HTML
```

The article metadata must be generated from the same canonical published article record used by the page.

Do not maintain a separate metadata database.

---

# 5. ONLY PUBLISHED CONTENT MAY GENERATE PUBLIC ARTICLE HTML

The public article route must resolve only content that is legitimately public.

Verify status rules.

At minimum:

```text
published → render article
draft → do not render public article
scheduled → do not render before publication
unpublished → do not render
missing → proper 404
```

Do not leak:

* drafts
* release-management metadata
* scheduling information
* editorial workflow fields

into public HTML.

The previous hardening work intentionally protected this data and that behavior must remain intact.

---

# 6. CANONICAL URL

For every article:

```text
<link rel="canonical" href="https://www.globalainews.in/article/<slug>">
```

Use the application's actual canonical domain/configuration.

Do not construct canonical URLs from:

* request host headers
* arbitrary forwarded hosts
* user-controlled parameters

Use a trusted configured public origin.

---

# 7. TITLE

Generate article titles server-side.

Prefer:

```text
<title>{article headline} | Global AI News</title>
```

unless the existing editorial/title strategy already provides an intentional alternative.

Do not create duplicate suffixes.

Do not allow:

```text
Headline | Global AI News | Global AI News
```

Do not use generic:

```text
Global AI News
```

for an article page.

---

# 8. META DESCRIPTION

Generate a meaningful description from the canonical article summary/dek.

Rules:

* use existing editorial data
* do not fabricate text
* do not keyword stuff
* do not dump the entire article body
* normalize whitespace
* truncate safely where required

Fallback order should be explicit and documented.

For example:

```text
article SEO description
→ article standfirst/dek
→ article summary
→ carefully derived fallback
```

If there is no legitimate fallback, use a concise generic publication description rather than inventing article-specific claims.

---

# 9. OPEN GRAPH

Generate server-side:

```html
<meta property="og:type" content="article">
<meta property="og:title" ...>
<meta property="og:description" ...>
<meta property="og:url" ...>
<meta property="og:image" ...>
<meta property="og:site_name" content="Global AI News">
```

Where article metadata supports it, also include:

```text
article:published_time
article:modified_time
article:author
```

Only emit values that are actually known.

---

# 10. TWITTER/X METADATA

Generate server-side:

```text
twitter:card
twitter:title
twitter:description
twitter:image
```

Use an appropriate card type supported by the existing image behavior.

Do not generate an image URL that does not exist.

---

# 11. ARTICLE IMAGE VALIDATION

Before writing:

```text
og:image
```

verify that the selected image is valid.

If no article image exists:

Use the site's legitimate default publication image.

Do not generate a broken image URL.

Do not point to an internal development asset.

---

# 12. PUBLISHED DATE

The first HTML response must contain the correct human-readable publication date.

Example:

```text
September 28, 2026
```

Machine-readable metadata may remain ISO:

```text
2026-09-28T...
```

Ensure:

```text
visible date
JSON-LD datePublished
OpenGraph published_time
```

all represent the same underlying publication event.

Do not modify publication timestamps merely for SEO.

---

# 13. MODIFIED DATE

Where a genuine modification exists, expose:

```text
dateModified
```

and optionally a visible:

```text
Updated September 29, 2026
```

Do not fabricate modification dates.

Do not change `updated_at` merely because an article was viewed, revalidated, or rebuilt.

---

# 14. AUTHOR

The first HTML response must include the correct readable author.

Example:

```text
By Ananya Rao
```

The author name should link to the canonical author profile.

Never emit:

```text
ananya-rao
```

as the reader-facing byline.

Never invent fallback authors.

If author information is genuinely unavailable:

```text
Byline unavailable
```

is acceptable.

---

# 15. ARTICLE JSON-LD

Generate valid server-side JSON-LD for appropriate article pages.

At minimum where applicable:

```text
@type
headline
description
image
datePublished
dateModified
author
publisher
mainEntityOfPage
```

The values must match the visible page and head metadata.

The author should reference the actual author profile URL where appropriate.

The publisher should reference the Global AI News organization.

Do not output schema claims that are not supported by the page.

---

# 16. BREADCRUMBS

If breadcrumbs are already implemented, ensure BreadcrumbList JSON-LD is generated in the first response too.

Keep the visible breadcrumb and structured-data breadcrumb consistent.

---

# 17. NO CLIENT-SIDE METADATA DEPENDENCY

Client-side code may enhance the page.

It must NOT be required for:

* title
* canonical
* description
* OG metadata
* Twitter metadata
* article JSON-LD
* primary H1
* primary author
* primary publication date
* primary article content

The initial HTML must already be correct.

---

# 18. DO NOT USE THE API AFTER HTML DELIVERY FOR PRIMARY SEO DATA

Avoid architecture like:

```text
GET /article/foo
→ generic HTML
→ JavaScript loads
→ API fetch
→ React changes <head>
```

The desired behavior is:

```text
GET /article/foo
→ Express resolves published article
→ HTML generated with real article metadata
→ browser receives correct HTML
→ optional hydration/enhancement afterward
```

---

# 19. FILE-MISSING FALLBACK

The existing article URL fallback that allows new article URLs to work without regenerating pre-rendered article files must remain.

Do not break the fallback.

However, distinguish:

```text
existing pre-rendered article
new API-backed article
missing article
```

All public article variants must still have correct first-response metadata.

---

# 20. ERROR RESPONSES

For a missing article:

Return an actual 404 status.

Do not return:

```text
200 + generic Global AI News HTML
```

for a nonexistent article.

Do not accidentally provide indexable generic metadata on article 404s.

Where appropriate:

```text
noindex
```

may be applied to error pages.

The requirement is:

# FINAL PRINCIPLE

The first HTML response is the canonical representation of the article for crawlers, previews, and users with JavaScript unavailable or delayed.

Therefore:

> **Never send generic article metadata first and repair it later with JavaScript.**

The publication must return the correct article identity immediately.
