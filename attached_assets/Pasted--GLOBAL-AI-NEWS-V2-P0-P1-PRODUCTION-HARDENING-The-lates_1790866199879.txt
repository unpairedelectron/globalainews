# PHASE 1 — SECURITY

## 1. Protect newsroom/release APIs

Audit every endpoint under:

```text
/api/newsroom/*
```

Identify which endpoints are public and which are editorial/admin-only.

At minimum investigate:

```text
/api/newsroom/releases
/api/newsroom/history
/api/newsroom/automation/status
```

The current production audit found that unauthenticated requests can retrieve release payloads and a non-publishable draft.

This MUST NOT remain public.

Implement actual authorization at the server/API layer.

Do NOT rely on:

* robots.txt
* X-Robots-Tag
* noindex
* client-side checks
* hidden UI

as the security mechanism.

A request from an unauthenticated user to an editorial/private endpoint must return an appropriate authorization response.

Do not expose:

* drafts
* unpublished releases
* scheduled editorial payloads
* internal release history
* automation state
* editorial workflow metadata

through public endpoints.

# PHASE 2 — SEPARATE PUBLIC AND PRIVATE DATA

Create a clear distinction between:

### PUBLIC

Published editorial data only.

### PRIVATE

Editorial workflow data.

The public API must never accidentally serialize private database columns.

Do not return entire Supabase rows where only selected fields are needed.

Use explicit field selection.

For example, conceptually:

```text
public article response
=
title
slug
summary
body
author
published_at
updated_at
sources
image
topics
```

not:

```text
entire database row
```

# PHASE 3 — HOMEPAGE FRESHNESS

The production audit found that the latest snapshot exists but is marked stale and the homepage remains tied to older content.

Determine exactly why.

Audit:

* Supabase data retrieval
* newsroom snapshot generation
* Next.js caching
* ISR
* fetch cache
* route cache
* Vercel cache
* client polling
* publishing workflow

The requirement is:

> Publishing an editorial story must not require a full application deployment for readers to see the new content.

Implement an explicit revalidation/invalidation mechanism.

The desired architecture is:

```text
editorial publish
        ↓
database mutation
        ↓
revalidation / cache invalidation
        ↓
homepage refresh
article refresh
topic refresh
author refresh where needed
sitemap refresh where needed
```

Use the correct Next.js mechanism for the current application architecture.

Do not convert the entire application to fully dynamic rendering unless necessary.

Preserve performance.

# PHASE 7 — HUMAN-READABLE BYLINES

Production article pages must display:

```text
By Ananya Rao
```

not:

```text
ananya-rao
```

Display the author's name from the actual author record.

The author name must link to:

```text
/author/<slug>
```

or the application's canonical equivalent.

Never invent an author.

If no valid author exists:

```text
Byline unavailable
```

is acceptable.

Do not use fallback attribution from:

* source publisher
* first database author
* editor
* ingesting user
* arbitrary default author

unless that fallback is an explicitly defined editorial rule supported by the product.
